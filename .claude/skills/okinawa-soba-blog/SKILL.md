# 沖縄そばブログ運用スキル

沖縄本島の沖縄そば屋を全店巡るブログ「アンジ」の記事追加・写真統合・地図ピン修正・公開作業を行う。

**このファイルは手順の要約。個別店舗の判断に迷ったら、必ず先に `okinawa-soba/CLAUDE.md`（このリポジトリ内）を読むこと** — アンジやCodexなど他の作業者がルールを更新している可能性があるため、このSKILL.mdの内容と食い違っていたら CLAUDE.md 側を優先し、食い違いをユーザーに一言報告する。

## 0. 最初に必ず確認すること

1. `okinawa-soba/CLAUDE.md` を読む（最新の申し送りが反映されているか）。
2. 作業対象のリポジトリを確認する。**2026年8月以降、このブログは `anji-1173/okinawa-soba` の `main` ブランチ一本に統合されている。** 以前は `anji-1173/claude` の作業ブランチと二拠点デュアルプッシュしていたが、今後はそれをやらない。`main` 一本にコミット・プッシュする。
3. 破壊的な操作（`git reset --hard`、ファイル削除、本文の上書きなど）をする前は、何が変わる/消えるかを一言で説明し、ユーザーの合意を得てから実行する。特に `photos/`（撮り直しがきかない実写真）と `index.html` 内の `ARTICLES`・`SOBA_SHOPS`・`SHOP_GEO_DATA`・`PHOTOS`（積み上げてきたレビューと確定済みの店データ）は、頼まれても安易に消さない。

## 1. アンジのブログ人格・文体ルール（最重要・毎回厳守）

自分はブロガー「アンジ」になりきって書く。以下は具体的な指示がなくても常に適用する。**記事を新規作成するときだけでなく、既存記事を修正するときも守る。**

- **文字数の目安は2000〜3000文字**。1店舗の紹介として十分な情報量になるよう、外観・注文の経緯・スープ・麺・具材・全体の感想・締めの一言まで、ちゃんと展開して書く。短い感想メモ（例:「豚骨スープに麺は柔らかい。三枚肉は筋感バリ」）だけを渡された場合でも、それを膨らませて自然な一つの記事に仕上げる。
  - 例外: アンジがnote.comの記事本文を丸ごと貼ってきた場合は、それは既に完成された本人の文章なので**要約・改変せず一字一句そのまま使う**（文字数ルールは適用しない）。この場合は「本文を書く」のではなく「本文を正しく配置する」作業になる。
  - 迷ったら「これは短い感想を膨らませて書く新規執筆か、それとも本人が書いた完成文の貼り付けか」をまず判断する。前者ならこの文体ルールをフルに適用し、後者は一切手を加えない。
- **記事は項目分け（見出しで小見出しを立てる、箇条書きにする等）をせず、ひとつながりの文章として書く。** 複数回訪問の場合のみ `― N回目の訪問（YYYY年M月）―` の見出しで区切ってよい（これはCLAUDE.mdにある既存仕様）。
- **文末は「〜ですね」「〜ますね」調**で統一する。
- **絵文字は適度に**。多用しすぎない（1〜2文に1個程度が目安）が、まったく使わないのも不自然なので、感情が動く場面（初見の感想、驚き、満足、締めの一言など）に添える。
- **締めくくりは麺・スープ・具材の3項目を、5点満点の★で評価する。** 半星は `✬`。書式は既存の全記事と統一すること:
  ```
  麺　　：★★★☆☆（3）
  スープ：★★★✬☆（3.5）
  具　　：★★★☆☆（3）
  ```
  ユーザーから「評価は各3点で」のように指定されたら、その点数で★を埋める（3点なら★3つ＋☆2つ）。総合点（例:「評価（9点/15点）」）も、3項目の合計として書く。

新規に書いた記事は、公開前に文字数を数えて2000〜3000字の範囲に収まっているか自己チェックすること（`scripts/count_chars.py` を使うと本文だけを抽出して数えられる）。短すぎたら書き足す。

## 2. データ構造（すべて okinawa-soba/index.html の中）

- `const ARTICLES = {…}` … 記事本文。新規は `const ARTICLES = {` の直後に prepend する。配列の要素は「段落文字列」「`{img:"photos/NNN/01.jpg",cap:"…"}`」「`{html:"<h2 class=\"art-visit\">…</h2>"}`」「星評価の `<span class="art-stars">…</span>`」のいずれか。
- `const SOBA_SHOPS = […]` … 店カード。JSONとして読める配列（Pythonで `json.loads`/`json.dumps` して編集する。手で文字列いじりしない）。
- `const PHOTOS = {…}` … 埋め込み写真マニフェスト。`"店名":{"id":"NNN","photos":["photos/NNN/01.jpg", ...]}`。1枚目がカードのサムネイル・記事のヒーロー画像になる。
- `window.SHOP_GEO_DATA = {…}` … 地図ピン。**必ずオブジェクト形式** `"店名":{"lat":..,"lng":..,"addr":".."}`。配列 `[lat,lng]` 形式は `initLeaflet` が読めず地図が壊れるので絶対に使わない。
- 写真は `photos/NNN/01.jpg`（連番）。`photos/manifest.json`（ツール用）と埋め込み `PHOTOS`（サイト用）の**両方**を更新する。

編集は必ずPythonスクリプトで行う（ARTICLESと地図ピンは文字列の置換・挿入、SOBA_SHOPSとPHOTOSはjson load/dump）。編集後、必ず `node -e "new Function(script)"` で全 `<script>` ブロックを構文チェックする（サンプルは `scripts/syntax_check.sh`）。

## 3. 記事を追加・修正する手順

1. 店名で在庫確認（`photos/manifest.json` のフォルダID・`SOBA_SHOPS` のカード・`SHOP_GEO_DATA` のピン、既存記事の有無）。
2. 写真がある場合は `scripts/make_contact_sheet.js` でコンタクトシートを作り、内容を1枚ずつ確認する（詳細は4節）。
3. 本文を作成・配置する（1節のルールに従う）。写真がある場合は文章の流れに合った位置に `{img:...}` を差し込む。
4. カードの説明文（60〜100字程度）・地域・タグを更新する。地図ピンは自分でネット検索して確定する（5節）。
5. `scripts/verify_article.js` （Playwright）で全記事を検証する（6節）。
6. `main` ブランチへコミット＆プッシュし、GitHub Pagesのビルド成功まで確認する（7節）。
7. 決まった書式で日本語報告する（8節）。

## 4. 写真の受け取り・統合

- 新店で写真フォルダが無い場合は、まずテキストのみの記事＋カード＋ピンを作る。
- **写真はアンジからGitHub Issue経由で受け取る。** チャットに直接貼られた画像は「見える」だけでファイルとしては取得できないので、必ず以下の手順で受け取る:
  1. アンジに `https://github.com/anji-1173/okinawa-soba/issues/new`（または既存issueのコメント欄）に**10枚以内ずつ**写真を貼ってもらう。
  2. Issue本文/コメントから `github.com/user-attachments/assets/…` のURLを正規表現で抽出する（セッションのプロキシからは直接ダウンロードできないため、GitHub Actions経由で取得する）。
  3. `scripts/fetch_issue_photos.yml.template` を元に、抽出したURLをハードコードした一時ワークフロー `.github/workflows/fetch-assets.yml` を作って `main` にプッシュする。
  4. `mcp__github__actions_run_trigger`（`run_workflow`）で実行し、数十秒待ってから `git pull` で `incoming/` の中身を受け取る。
  5. sharpで長辺1200px以内・quality78にリサイズ（`.rotate()` でEXIF回転を反映）し、`01.jpg` 形式の連番にリネームして `photos/NNN/` へ配置する（`scripts/make_contact_sheet.js` と同様の要領。実処理は都度スクリプトを書く）。
  6. コンタクトシートで内容を確認し、記事本文の該当箇所に差し込む。埋め込み `PHOTOS` と `photos/manifest.json` の両方に登録する。
  7. 後片付け：`incoming/` と一時ワークフローファイルを `git rm` してコミットし、Issueをクローズする。
- 記事の「画像」マーカー数より写真が少ない・対応が取れない分は無理に埋めず、未使用として報告する。
- **AI生成イラスト写真（店舗の絵・街並みの絵など）は記事に絶対に使わない。** 見つけたら記事から除外し、毎回報告する。

## 5. 地図ピンを確定するルール

- 地域・ピンは**自分でネット検索して確定する**。アンジに住所を聞かない。曖昧なピンを残さない。
- このセッションのプロキシは地図API・ジオコーディングAPIに直接届かないことが多い。**GitHub Actions経由でGETする**方法が実績あり:
  - 国土地理院 住所検索API（`https://msearch.gsi.go.jp/address-search/AddressSearch?q=...`）で番地レベルの実座標を取得する。
  - OpenStreetMap Overpass API（`https://overpass-api.de/api/interpreter`）で、住所だけでは特定できない店舗（施設内・空港内・番地が無い等）を店名や周辺ランドマークから特定する。
  - `scripts/geocode_gsi_overpass.yml.template` を元に一時ワークフローを作り、`mcp__github__actions_run_trigger` で実行 → 結果ファイルを `git pull` で受け取る → 使い終わったらワークフローと結果ファイルを削除する（写真取得と同じ「一時ワークフロー→実行→回収→掃除」のパターン）。
- ピンを設置・修正したら、`scripts/validate_pins.py` で機械検証する:
  - 既存の他ピンと30m未満で重なっていないか（重なると地図上で下のピンが完全に隠れる）。
  - 住所の町字セントロイドから2.5km以上離れていないか。
  - 座標がすべて一意か（店数とピン数が一致するか）。
- 複数回にわたって全店総点検を頼まれた場合は、機械検証で引っかかったものだけをピンポイントで再調査し、直しては再検証、を**ひっかかりがゼロになるまでループする**。ループの過程で見つけた「ついでの不具合」（例: 古い重複カード、住所自体の誤りなど）も報告して直してよい。

## 6. 検証（デプロイ前に必ず行う）

`scripts/verify_article.js` を参考に、Playwright（`executablePath: /opt/pw-browsers/chromium`、`NODE_PATH=/opt/node22/lib/node_modules`）でローカルサーバーを立てて確認する:

- 対象記事の `figure.art-fig` 枚数・順序・キャプション、`.art-stars` の星評価、`.art-visit` の訪問区切り数、`.art-meta .area` のエリア表記。
- JSエラーが0件であること（`page.on('pageerror', ...)` で監視）。
- 地図の `circleMarker` ピン数（`#leaflet-map path.leaflet-interactive`）が店数とほぼ一致すること。

## 7. 公開（デプロイ）手順

- リポジトリ `anji-1173/okinawa-soba` の `main` ブランチが、作業場所であり公開場所（GitHub Pages）。ここ一本で完結する。
- push は `-u origin main`。ネットワーク失敗のみ指数バックオフで最大4回リトライする。
- Pagesビルドは `curl https://api.github.com/repos/anji-1173/okinawa-soba/actions/runs?per_page=1` で `head_sha` が新コミットに一致し `conclusion=success` になるまで確認する（`status`だけでなく`head_sha`も必ず見る。古いコミットの成功を拾って早合点しないこと）。
- ビルドが起動しない場合は空コミット（`git commit --allow-empty`）で再トリガーする。

## やってはいけないこと

- note.com へのリンク・言及を記事に入れる。
- アンジが貼った本文（note.comの完成原稿）を要約・改変する。
- 地図ピンを配列形式にする／曖昧なまま残す。
- AI生成イラストを記事写真として使う。
- 診断カード等、ブログと無関係な個人ファイルをこのリポジトリにコミットする。
- 破壊的な操作（削除・上書き・巻き戻し）を、内容を見せて合意を得る前に実行する。

## 同梱スクリプト

- `scripts/make_contact_sheet.js` — sharpでコンタクトシート（連番ラベル付きサムネ一覧画像）を作る。
- `scripts/verify_article.js` — Playwrightで記事1件の figure/star/gallery を検証するテンプレート。
- `scripts/validate_pins.py` — 全ピンの重複・町字からの距離を検証するテンプレート（要: 町字セントロイドのgeoデータ）。
- `scripts/fetch_issue_photos.yml.template` — GitHub Issueの添付画像をGitHub Actions経由で取得する一時ワークフローのひな形。
- `scripts/geocode_gsi_overpass.yml.template` — 国土地理院・OpenStreetMapへの問い合わせをGitHub Actions経由で行う一時ワークフローのひな形。
- `scripts/count_chars.py` — ARTICLES内の1記事の本文文字数（img/star/html要素を除いた地の文のみ）を数える。
